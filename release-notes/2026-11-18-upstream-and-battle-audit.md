### 1. 新旧装备 ID 不兼容（已复现）

上游 `gearKey('AJ0160@c2')` 返回该登升编号；Moon 返回空字符串。Moon 的 `normalize` 和 `normalizeLoadout` 因此会过滤登升条目。上游四栏存于 `record.arsenalLoadouts`，Moon 从 `record.loadouts[heroId]` 创建小队并备战，两者没有自动映射。

如果只覆盖界面或导入新版存档，会出现库存/配装缺项；现有 `equipmentName` 和卡图查询也需要按基础 ID 查找、同时保留登升循环。不能仅放宽一个正则就宣称兼容。

建议：保留英雄为实际参战单位，把四栏和方案作为模板；导入时明确选择目标英雄、执行一次带修订号和库存验证的保存。针对配装不应同时占用实装库存。旧格式迁移要保留原字段并可重复运行，不能把现有英雄配置覆盖为空。

### 2. 上游登升扣费丢响应后会重复扣费（故障注入已复现）

上游 `technology/index.html` 的 `ascendArsenalGear` 先调用 `changeAscensionCore` 扣 theatre 核心，再写 record 装备和收据。操作 ID 尚未保存时，第一次扣费已经成功但响应丢失，函数直接退出；重试时没有装备收据，于是再次扣费。

只替换 I/O、运行上游原函数的本地故障注入：初始核心 3、装备 1；第一次核心扣到 2 后模拟断线；重试完成一次登升后，核心为 1。结果应为 2，实际多扣 1。此问题在上游，Moon 基线尚未引入该功能。

建议：在 CampaignAccount 内用一个稳定操作 ID，在同一事务验证库存/预占、扣核心、转移装备并保存操作收据。重试只返回已有结果。不要把客户端补偿退款当作跨 section 的原子提交。

复现：`cd cloudflare && node review-upstream.mjs d591315`。此脚本读取指定 Git 提交，使用隔离内存状态，不写仓库及线上存档；它用于审计已知版本，不是断言修复后仍须保留该缺陷的回归测试。

### 优化建议与尚未覆盖的规则

以下属于当前人工辅助流程的缺口，不能把它们说成已有自动结算器算错了：

1. **攻击结束结算。** 现在掷骰、转换、池清空均为独立操作。可增加攻击记录，区分本次可用的旧标记与本次产生的新标记，再提供“结束攻击”动作，避免一次清空误删新标记。不能用“下一轮清空池”代替攻击结束。
2. **同时多次生死关头。** 第 43 页规定同时被迫执行多次生死关头抽取则即刻死亡。当前 API 每次只接收单个来源，不能判断“同时”还是连续独立事件；建议增加同次效果来源确认和死亡提示。不要把任意两张尚未归还的牌直接当作同时触发。
3. **重掷费用可追溯。** 当前 UI 说明由玩家结算重掷和转换来源。可提供命运/装备/其他效果来源记录；只有选择命运时才自动调整命运，不能把所有重掷统一收费。
4. **配装槽位和卡文例外。** 当前小队主要检查库存，不是完整的装备规则验证器。可先提示武器、护甲、支援及附件槽位，再逐步补齐特殊泰坦、附件和卡文例外；不要只凭数量一律硬拦。

未覆盖全部骇物特例、全部故事集卡文、真人联机竞争、断网重连和前端浏览器操作。视线测试通过说明实现符合现有测试场景，不代表新增了 115 条独立官方规则裁决。
